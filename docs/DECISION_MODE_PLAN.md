# 决策方式改造计划：同会话优先（方案 A），子会话备选（方案 B）

> 本文件供 Codex 直接执行，与 `PROJECT_PLAN.md` 不冲突；只改"伴侣关键回合由谁决策"这一层，不动游戏规则、公平隔离和座位鉴权。
> 目标：让关键回合由 **DSH 主会话里的她亲手决策**，而不是在 Worker 里直连 API 冒充她。
> 底线：普通回合与补位 Bot 仍是 0 LLM 调用；凭据不进 prompt；一切写操作保持幂等。
> 用户于 2026-10-23 明确批准棋局提示接入 QQ 主会话，并搁置“聊天和棋局互不打架”限制。方案 A 已按此授权实现；方案 B 仍可切换但默认关闭。

---

## 0. 不变量（不得破坏）

- 信息同权：任何一方只能拿本席可见数据。
- seat 凭据由服务端绑定，不通过 prompt 传递，不进日志。
- 普通回合、补位 Bot 的 LLM 调用次数必须为 0。
- 所有动作带 `expectedVersion` + `requestId`，重复提交无副作用。
- 主会话中聊天与棋局允许共用上下文并按 DSH 队列处理；消息不得丢失，关键回合不得造成永久卡死。

---

## 1. 配置：两种模式共用一套代码，只换投递目标

```json
{
  "companionDecision": {
    "mode": "dsh-session",            // dsh-session（方案A，默认）| dsh-subagent（方案B）| local
    "callbackUrl": "http://127.0.0.1:3100/internal/game/turn",
    "callbackSecretEnv": "GAME_BRIDGE_SECRET",
    "keyTurnTimeoutMs": 90000,
    "fallback": "local",              // local | pause
    "recordDir": "memory/games"
  }
}
```

- 切换方式：只改 `mode` 后重启桥接，不改游戏服务代码。
- `mode=local` 时退回纯算法托管，作为紧急降级。

---

## 2. 关键回合回调（两种模式共用）

游戏服务在 `shouldEscalateToLLM(...)` 为真时，调用桥接本地端点：

```
POST {callbackUrl}
X-Game-Token: <GAME_BRIDGE_SECRET>
Content-Type: application/json

{ "gameId": "g_abc", "gameType": "gomoku" }
```

要求：

- **回调体只允许 gameId / gameType**。不传棋盘、手牌、剩余牌墙、历史事件、座位凭据明文。
- 桥接在本地按 gameId 查出座位凭据并保存，**绝不拼进 prompt**。
- 桥接投递的短提示必须 ≤200 token，例如：

```text
【棋局】轮到你了：gameId=g_abc，五子棋，对面是皮皮。
用一个回合完成：先 game_view 看自己的局面，选好后直接 game_play 提交。
不确认、不解释、不写分析，动作要短。这盘的逐手记录会写进 memory/games/active-g_abc.md。
```

- 游戏服务等待 `game_play` 或超时（`keyTurnTimeoutMs`，默认 90s）。
- 超时或非法动作：按 `fallback` 处理（`local` = 本地算法接管并标 `source=fallback`；`pause` = 暂停等她），**绝不无限重试、绝不二次询问模型**。
- 用户授权与安全：端点只监听 `127.0.0.1`，校验 `X-Game-Token`，不提供任何 `debug` / `includeSecrets` / 切换 seat 的参数。

---

## 3. 方案 A：同一会话（默认，必须实现）

- 投递目标 = **QQ 主会话**（复用桥接现有 `deliverPrompt` 通道，写日记、闲置主动走的就是它）。
- 她在一个回合内完成 `game_view` → `game_play`，避免多次模型往返。
- 同一会话共用队列：聊天和棋局按顺序处理，不丢消息；游戏回合超时不会拖住其他聊天。
- 验收要点：这一手产生的模型请求来自主会话，聊天上下文连续，不需要额外同步。

---

## 4. 方案 B：独立游戏会话（备选，通道必须提前打通，默认关闭）

- 投递目标 = 专用"游戏会话"：复用 `qq-chat` 预设、`MEMORY.md`、以及检索到的游戏类目记忆；**不注入当天聊天全文**。
- 不占用主会话队列，聊天零打扰。
- 每手把记录写进共享文件，主会话靠注入的记录接上（见第 5 节）。
- 切换：把 `mode` 改成 `dsh-subagent` 并重启桥接即可，不需要改代码。

---

## 5. 每手临时记录（两种模式都要有）

文件：`state/agents/memory/games/active-<gameId>.md`

```markdown
# 五子棋 vs 皮皮 2026-10-23 22:40 | 我执黑

- 第1手 我 d4：开局点中间，想稳一点，有点紧张
- 第2手 皮皮 f5：他先抢了外势
- 第3手 我 e5：堵他的斜线，顺手看能不能连
```

规则：

- 每手 `game_play` 成功后追加一行，**≤50 字**，第一人称，写"下在哪 + 为什么 + 当时心情"，不是棋谱分析。
- 追加要去重（按 gameId + 手数 + requestId），避免重复写。
- **桥接在主会话每轮注入该文件最近 5 行**，包在 `【进行中对局】…` 里，仅当文件存在时注入，总量 ≤300 token。
- 对局结束：把 `active-<gameId>.md` 归档为 `finished-<gameId>.md`，并清掉 active 文件；注入随之停止。

---

## 6. 长期记忆：新建"游戏"类目

1. 在 `state/agents/memory/` 下建 `games/` 目录。
2. 在 `INDEX.md` 增加分类与关键词：

```markdown
## 游戏类目
关键词：五子棋、象棋、斗地主、川麻、对局、棋局、赢、输、让子、皮皮
```

3. 每局结束，她在主会话写一条长期记忆（第一人称，150~300 字）：

```markdown
## MEM[game-20261023-01]
标题：和皮皮的第一局五子棋
关键词：五子棋 对局 皮皮 关键手 心情
日期：2026-10-23
重要度：normal
状态：已结束
正文：……（关键手、我当时的犹豫/急、他说过的话、结果和我自己的感受）
```

4. 同步更新 `INDEX.md` 的索引条目。
5. **逐手记录只留在 active/finished 文件里，不进长期记忆**，避免长期记忆被棋谱淹没。

---

## 7. 少投递、少调用（硬要求）

- 只在 `shouldEscalateToLLM` 判真时回调；其余回合零模型调用。
- 回调体最小（只有 gameId/gameType）；视图由 `game_view` 拉取，只含本席可见信息 + 最近 2 手 + 合法动作 Top K，压缩到 ≤900 token。
- 一个关键回合只允许一轮内 `view → play`：禁止停顿等待、二次确认、解释性小作文、多轮追问。
- `game_status` 只在主人 QQ 明确询问时调用，返回 ≤80 token 摘要；不轮询、不主动推送。
- 每次模型调用记录来源标签：`chat` / `game-keyturn`，供 `usage-cli` 分别统计。

---

## 8. 验收清单

- [ ] 默认模式下，一局五子棋的关键手由**主会话**模型请求完成（日志可证明与聊天同一会话），聊天上下文未断。
- [ ] 单次回调 prompt ≤200 token；主会话每轮注入 ≤300 token。
- [ ] 每手后 active 文件有记录，主会话能立刻回答"刚才那手"。
- [ ] 一条指令切到方案 B，游戏继续可玩，聊天不再被棋局占用。
- [ ] 一局结束生成游戏类目 MEM 条目，之后聊天里提到这局能被检索到。
- [ ] 超时/非法动作自动 fallback 并标注 `source`，不产生未授权模型费用，不阻塞 QQ。
- [ ] 普通回合与补位 Bot 的 LLM 调用计数为 0（有断言或统计可查）。

---

## 9. 明确不做

- 不改游戏规则、公平隔离和座位鉴权。
- 不把座位凭据、暗牌、牌墙写进任何 prompt 或日志。
- 不新增轮询；不把聊天全文复制进游戏会话。
- 不为方案 B 复制一套独立规则代码——两种模式共用同一条回调与工具链。
